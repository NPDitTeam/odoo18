# ตัวช่วย AI-IT (npd_ai_it_assistant)

เพิ่มแท็บ **"ตัวช่วย AI-IT"** ในเมนูสนทนา (ไอคอนแชทมุมขวาบน) ต่อจากแท็บ
ทั้งหมด / สนทนา / ช่องทาง แท็บนี้แสดง "หัวข้อปัญหา" ที่ให้ AI ช่วยแก้ให้
แทนที่จะเป็นรายการห้องแชท

## หัวข้อที่ 1 — แก้ปัญหาตัดสต็อกไม่ได้เนื่องจากสต็อกไม่พอ

ขั้นตอนที่พนักงานเจอ:

1. กดแท็บ **ตัวช่วย AI-IT** แล้วเลือกหัวข้อที่ 1 → ระบบเปิดห้องแชทกับผู้ช่วยให้
2. ผู้ช่วยถาม **เลขที่เอกสาร** (ใบสั่งขาย เช่น `S00123` หรือเลขใบจัดส่ง)
3. ระบบตรวจ **คลังของสาขาที่พนักงานสังกัด** แล้วตอบว่าสินค้าตัวไหนไม่พอ
   พร้อมบอกว่าต้องตัดเท่าไร / ในระบบมีเท่าไร / ขาดอีกเท่าไร
   - **หาคลังของสาขาไม่เจอก็ไม่ต้องรอ IT** เช่น สาขาเปิดใหม่อย่าง "สำนักงานใหญ่"
     ที่ยังไม่มี location — ตัวช่วยจะสร้างคลังของสาขาให้เอง แล้วเดินเรื่องต่อทันที
     (คลังใหม่สต๊อกเป็น 0 ทุกตัว จึงเข้าขั้นตอนถามจำนวนสต็อกจริงตามปกติ)
   - ถ้ามีคลัง **ชื่อเดียวกับสาขา** อยู่แล้วแต่ยังไม่ได้ผูกสาขาไว้ จะ *ผูกให้*
     แทนการสร้างซ้ำ — สต๊อกเดิมที่มีอยู่ยังอยู่ครบ
   - ปิดความสามารถนี้ได้ที่ System Parameter
     `npd_ai_it_assistant.auto_create_branch_location = 0` (ค่าเริ่มต้นคือเปิด)
4. ถ้าไม่พอหลายตัว ผู้ช่วยจะถาม **จำนวนสต็อกจริง** ของสินค้า *แต่ละตัว*
   ตอบได้หลายแบบ เช่น `1=10, 2=5` หรือพิมพ์ทีละบรรทัด หรือพิมพ์เป็นประโยค
5. ผู้ช่วยสรุปให้ดูก่อน แล้วพนักงานพิมพ์ **"ยืนยัน"**
6. ระบบเติมสต๊อกให้ แล้วถามว่าจะให้ตัดสต๊อกต่อเลยไหม
7. พิมพ์ **"ทำต่อ"** → ระบบเรียกตรรกะเดียวกับปุ่ม **"ตัดสต็อก Auto 🚚"** ให้เลย
   ไม่ต้องกลับไปที่เอกสาร แล้วรายงานผล (รวมคำเตือน) กลับมาในแชท
   ถ้าอยากไปกดปุ่มเองก็พิมพ์ **"ไม่ต้อง"**

## หัวข้อที่ 2 — แก้ไขวันที่ใบแจ้งหนี้

พนักงาน **คัดลอก URL ของหน้าใบแจ้งหนี้** มาวาง (ไม่ใช้เลขที่เอกสาร เพราะฉบับร่าง
ยังไม่มีเลขที่ แต่ URL มี `id` เสมอ) เช่น

```
http://localhost:8079/web#id=66121&model=account.move&view_type=form&cids=1&menu_id=486
```

ระบบดู **ประเภทสินค้า** (`account.move.reason_code_id`) กับสถานะ แล้วแยกทาง:

| ประเภทสินค้า | สถานะ | ระบบทำอะไร |
| --- | --- | --- |
| ทุกประเภทที่รองรับ | ลงบันทึก / ชำระแล้ว | ยืนยันก่อน → ยกเลิกการชำระ → ยกเลิกเอกสาร → **แจ้งให้ไปสร้างเอกสารใหม่** |
| สินค้าหาย / ค่าเช่าส่วนต่าง / สินค้าชำรุด | ฉบับร่าง | ให้พนักงานระบุวันที่เอง — **ต้องอยู่ในเดือนเดิม ห้ามข้ามเดือน** |
| ใบแจ้งหนี้ค่าเช่า | ฉบับร่าง | ดึง **วันที่สั่งซื้อ** จาก `sale.order` ที่ผูกผ่านช่อง Source Document มาใส่ให้เอง |
| ใบแจ้งหนี้ค่าเช่า + สมุดรายวันลดหนี้ขาย | ฉบับร่าง | ให้พนักงานระบุวันที่เอง (ไม่ดึงจากใบสั่งขาย) — ห้ามข้ามเดือน |

**ทุกครั้งที่แก้วันที่ ต้องพิมพ์หมายเหตุว่าแก้เพราะอะไรก่อน แล้วจึงกดยืนยัน**
(ขั้นตอน: วันที่ → หมายเหตุ → สรุปก่อน/หลัง → พิมพ์ "ยืนยัน" → ระบบจึงลงมือ)
ระบบบันทึกลงประวัติ (chatter) ของเอกสาร พร้อมชื่อคนแก้และค่าก่อน/หลัง

รูปแบบวันที่ที่พิมพ์ได้: `25` / `25/8` / `25/08/2026` / `25/8/69` (พ.ศ.) /
`2026-08-25` / `25 ส.ค. 69` / `25 สิงหาคม 2569`

### การตั้งค่าเพิ่มเติม

สมุดรายวันลดหนี้ขายเทียบจากชื่อ/รหัส เปลี่ยนได้ที่ System Parameters:

| Key | ค่าเริ่มต้น |
| --- | --- |
| `npd_ai_it_assistant.credit_note_journal_names` | `สมุดรายวันลดหนี้ขาย` |
| `npd_ai_it_assistant.credit_note_journal_codes` | `CN` |

### ⚠️ ผลข้างเคียงที่ต้องรู้

การยกเลิกเอกสารรันด้วย `sudo()` ตามที่ตกลงไว้ แต่โมดูล `user_cancel_control`
เช็ค `env.user.allow_cancel` ตอน `button_draft()` และผู้ใช้ระบบ (`__system__`)
ไม่ได้ถูกติ๊กไว้ โมดูลนี้จึง **ติ๊ก `allow_cancel` ให้ผู้ใช้ระบบตอนติดตั้ง**
(ดู `hooks.py`) — ปลดล็อกเฉพาะโค้ดที่รันในนามระบบ พนักงานที่กดปุ่มบนหน้าจอ
ยังถูกด่านเดิมคุมอยู่ครบ ถ้าไม่ต้องการ ให้ติ๊ก `allow_cancel` ของ `__system__` ออก

## หัวข้อที่ 3 — แก้ไขวันที่คืนสินค้า

แก้ฟิลด์ **วันที่และเวลาคืน** (`stock.picking.return_date`) ซึ่งหน้าจอล็อกไว้
แก้ไม่ได้ถ้าผู้ใช้ไม่มีสิทธิ์ `can_edit_force_date` (โมดูล `rental_stock_picking`)

1. พิมพ์ **เลขที่ใบคืน** เช่น `W3/IN/08511` — **รับเฉพาะใบคืน (ใบรับเข้า) เท่านั้น**
   ใบส่งออกจะถูกปฏิเสธ พร้อมบอกว่าเอกสารที่ให้มาเป็นประเภทอะไร
2. ระบบแสดงใบคืนนั้นเป็นการคืนของใบไหน + วันที่คืนปัจจุบัน
3. พิมพ์ **วันที่คืนใหม่**
4. พิมพ์ **เหตุผล** ที่แก้
5. ตรวจทาน แล้วพิมพ์ **"ยืนยัน"**

ต่างจากหัวข้อ 2 ตรงที่ **ไม่บังคับให้อยู่ในเดือนเดิม** เพราะวันที่คืนของจริงข้ามเดือนได้

### ด่านที่กันไว้

| เงื่อนไข | ผล |
| --- | --- |
| ไม่ใช่ใบรับเข้า (`picking_type_id.code != 'incoming'`) | ปฏิเสธ |
| ใบถูกยกเลิก | ปฏิเสธ |
| **สถานะการคืนเงินประกัน = "คืนเงินแล้ว"** (`deposit_return_state = 'returned'`) | **ปฏิเสธ** ให้ติดต่อฝ่ายบัญชี/การเงิน |
| เอกสารอยู่คนละสาขากับพนักงาน | ปฏิเสธ |

ด่านคืนเงินประกันถูกเช็ค **2 รอบ** — ตอนรับเลขเอกสาร และอีกครั้งก่อนเขียนจริง
เผื่อสถานะเปลี่ยนระหว่างที่คุยกันอยู่

> `return_date` เป็น Datetime เก็บเป็น UTC โค้ดจึงแปลงเวลาผู้ใช้ ↔ UTC ให้
> (`to_local` / `to_utc` ใน `models/ai_it_picking_fix.py`) ถ้าเขียนตรง ๆ
> วันที่จะเพี้ยนไปตามโซนเวลา
>
> ในแชทแสดงและถามเฉพาะ **วันที่** ส่วนเวลาคงค่าเดิมของเอกสารไว้เงียบ ๆ
> (พิมพ์เวลามาด้วยก็ยังรับ แต่ไม่ได้โฆษณาไว้) ถ้าอยากดูค่าเป๊ะ ๆ ดูได้ที่
> tracking ของฟิลด์ซึ่ง Odoo บันทึกให้อยู่แล้ว

## หัวข้อที่ 4 — แก้ไขสถานะการเช่า

ถอยสถานะ `sale.order.rental_status` ซึ่งเป็นฟิลด์ **computed + store** และหน้าจอ
ตั้ง readonly ไว้ (โมดูล `pfb_npd_add_date_quatation_order`)

1. พิมพ์ **เลขที่ใบสั่งขาย** เช่น `SO-25100600028`
2. ระบบคำนวณสถานะที่ถูกต้องให้เอง — **ไม่ต้องเลือกสถานะ**
3. ระบุ **เหตุผล** แล้ว **"ยืนยัน"**

### กติกาคำนวณสถานะ

เทียบวันนี้กับ **วันที่สิ้นสุดการเช่า** (`end_rent_date`):

| เงื่อนไข | สถานะใหม่ |
| --- | --- |
| วันนี้ **เกิน** วันสิ้นสุดการเช่า | `overdue` — เกินกำหนด |
| วันนี้ **ยังไม่ถึง** วันสิ้นสุดการเช่า | `due_date` — ครบกำหนด |

ถ้าสถานะปัจจุบันตรงกับที่คำนวณได้อยู่แล้ว บอทจะบอกว่าไม่ต้องแก้ ไม่ไปเขียนซ้ำ

### ด่านที่กันไว้

| เงื่อนไข | ผล |
| --- | --- |
| **สถานะการเช่าปัจจุบันไม่ใช่ "ปิดบิล"** (`rental_status != 'done'`) | **ปฏิเสธ** — เมนูนี้มีไว้ "ถอย" สถานะ จึงต้องเริ่มจากใบที่ปิดบิลแล้ว |
| มีเอกสาร **คืนเงินประกันค่าเช่า** (`account.voucher` ชนิด `purchase`, เลข `CP-`) ที่ `reference` = ชื่อ SO และ `state = 'posted'` | **ปฏิเสธ** ให้ติดต่อฝ่ายบัญชี/การเงิน |
| ไม่มี `end_rent_date` | ปฏิเสธ (คำนวณไม่ได้) |
| เอกสารอยู่คนละสาขากับพนักงาน | ปฏิเสธ |

ด่านสถานะและด่านคืนเงินประกันเช็ค **2 รอบ** เหมือนหัวข้อ 3 — ตอนรับเลขเอกสาร
และก่อนเขียนจริง เผื่อมีคนไปเปลี่ยนระหว่างที่พนักงานกำลังคุยกับบอทอยู่

> เขียนค่าด้วย `order.write({'rental_status': ...})` แบบเดียวกับ wizard เดิมของระบบ
> (`npd_rental_status_update`) — `rental_status` เป็น computed+store ที่ `@api.depends`
> อยู่กับ `invoice_ids`, `end_rent_date`, `origin`, `pfb_so_type` ถ้าฟิลด์พวกนี้
> เปลี่ยนทีหลัง ระบบอาจคำนวณทับค่าที่แก้ไว้ได้ — บอทเตือนเรื่องนี้ในข้อความสรุปด้วย

## หัวข้อที่ 5 — แก้การปัดเศษ VAT ในใบแจ้งหนี้ (สลับได้ทั้งไปและกลับ)

ใช้ตอนลูกค้าทักว่า **"ยอดก่อน VAT ต่างจากที่ผมคิดไป 1 สตางค์"**

ยอดรวม 4,515.00 บาท แยกฐาน/ภาษีได้สองแบบ **ถูกทั้งคู่** ต่างกันแค่ปัดเศษตอนไหน:

| แบบ | ก่อน VAT | VAT 7% | วิธีคิด |
| --- | --- | --- | --- |
| **แบบรายบรรทัด** | 4,219.62 | 295.38 | ปัด VAT ทีละบรรทัดแล้วค่อยรวม — ค่าตั้งต้นของ Odoo |
| **แบบยอดรวม** | 4,219.63 | 295.37 | ปัดครั้งเดียวจากยอดรวม — ที่ลูกค้าคิดเอง (4,515 ÷ 1.07) |

1. พิมพ์ **เลขที่ใบแจ้งหนี้** หรือวาง **URL** ของหน้านั้น
2. บอทเทียบให้ดูทั้งสองแบบ พร้อมบอกว่า **ตอนนี้ใบนี้เป็นแบบไหน**
3. พิมพ์ **1** (แบบยอดรวม) หรือ **2** (แบบรายบรรทัด)
   — เคยให้แก้เป็นแบบยอดรวมไปแล้วอยากได้ของเดิมคืน พิมพ์ **"ถอยกลับ"** ได้เลย
4. ระบุ **เหตุผล** แล้ว **"ยืนยัน"**

**ยอดรวมทั้งใบไม่เปลี่ยน** ย้ายแค่เศษสตางค์ระหว่างช่องก่อน VAT กับช่อง VAT
ยอดที่ลูกค้าต้องจ่ายจริงและภาษีหัก ณ ที่จ่ายจึงเท่าเดิม

### แก้ครบ 4 ที่ — ข้อ 4 คือข้อที่ลืมกันบ่อยที่สุด

| # | ตาราง | แก้อะไร |
| --- | --- | --- |
| 1 | `account_move_line` บรรทัดรายได้ | `price_subtotal` + เดบิต/เครดิต/`balance`/`amount_currency` |
| 2 | `account_move_line` บรรทัดภาษี | ยอดภาษี + `tax_base_amount` |
| 3 | `account_move` | `amount_untaxed` / `amount_tax` (+ `_signed`) |
| 4 | **`account_move_tax_invoice`** | `tax_base_amount` / `balance` — ตารางที่ออก **รายงานภาษีขาย (ภ.พ.30)** ถ้าลืม ใบกับรายงานภาษีจะไม่ตรงกัน |

เขียนด้วย SQL เพราะฟิลด์พวกนี้เป็น stored compute ถ้าเขียนผ่าน ORM Odoo จะคำนวณ
ทับกลับทันที (โมดูล `npd_rent_price_round` ที่คุมการปัดเศษของระบบก็เขียนด้วย SQL
ด้วยเหตุผลเดียวกัน)

การกระจายเศษลงบรรทัดใช้วิธี **largest remainder** — ปัดลงทุกบรรทัดก่อน แล้วยกเศษ
สตางค์ที่เหลือให้บรรทัดที่เศษมากที่สุด ได้ผลเหมือนเดิมทุกครั้งที่คำนวณซ้ำ

### ด่านที่กันไว้

| เงื่อนไข | ผล |
| --- | --- |
| ไม่ใช่ใบแจ้งหนี้ขาย/ใบลดหนี้ขาย | ปฏิเสธ |
| **ยังไม่ลงบันทึก** (ฉบับร่าง) | ปฏิเสธ — ให้ติ๊กช่อง "คำนวณ VAT จากยอดรวม" ที่หน้าจอแล้วกดบันทึก ระบบคำนวณให้เอง |
| สกุลเงินไม่ใช่สกุลเดียวกับบริษัท | ปฏิเสธ (ต้องแปลงค่า `amount_currency` เพิ่ม) |
| มีบรรทัดภาษีมากกว่า 1 / ไม่ใช่ VAT 7% / ไม่ใช่ภาษีรวมในราคา | ปฏิเสธ |
| มีบรรทัดสินค้าที่ผูกภาษีไม่ตรงกับบรรทัดอื่น | ปฏิเสธ — หารยอดรวมด้วย 1.07 ทั้งก้อนไม่ได้ |
| ยอดก่อน VAT ที่หัวใบไม่ตรงกับผลรวมของบรรทัด | ปฏิเสธ — ใบเพี้ยนมาก่อนแล้ว ให้คนดูก่อน |
| **ส่วนต่างเกิน 0.05 บาท** | ปฏิเสธ — เมนูนี้มีไว้แก้เศษปัดเท่านั้น ห้ามกลายเป็นเครื่องมือแก้ยอดตามใจ |
| เอกสารอยู่คนละสาขากับพนักงาน | ปฏิเสธ |

ถ้าปัดแล้วสองแบบได้เลขเท่ากัน บอทบอกว่า "ไม่มีเศษให้แก้" แล้วจบ ไม่ไปเขียนซ้ำ
ด่านทั้งหมดเช็ค **2 รอบ** เหมือนหัวข้ออื่น — ตอนรับเอกสาร และก่อนเขียนจริง

ก่อน commit ยังมีด่านสุดท้ายอีกชั้น: **เดบิตต้องเท่ากับเครดิต** และผลรวม
`amount_currency` ต้องเป็นศูนย์ ถ้าไม่ผ่านจะ `raise` ให้ทรานแซกชันย้อนกลับทั้งก้อน
ใบกลับเป็นค่าเดิมทุกช่อง

> **ผลข้างเคียงที่ต้องบอกฝ่ายบัญชี:** ยอดภาษีขายของใบนั้นเปลี่ยนไป 1 สตางค์
> ถ้ายื่น ภ.พ.30 ของเดือนนั้นไปแล้ว ต้องแจ้งให้ทราบ — บอทเตือนไว้ในข้อความสรุปด้วย

## ประวัติการแก้ AI-IT

ทุกงานที่ทำ **สำเร็จ** จะถูกบันทึกลงตาราง `npd.ai.it.history` หนึ่งบรรทัด
ไม่ว่าจะมาจากหัวข้อไหน:

| ประเภทการแก้ | มาจาก |
| --- | --- |
| เติมสต๊อกให้พอตัด | หัวข้อ 1 ขั้นเติมสต๊อก |
| ตัดสต๊อกให้ | หัวข้อ 1 ขั้น "ทำต่อ" |
| แก้วันที่ใบแจ้งหนี้ | หัวข้อ 2 |
| ยกเลิกใบแจ้งหนี้ | หัวข้อ 2 |
| แก้วันที่คืนสินค้า | หัวข้อ 3 |
| แก้สถานะการเช่า | หัวข้อ 4 |
| แก้การปัดเศษ VAT ใบแจ้งหนี้ | หัวข้อ 5 |

แต่ละบรรทัดเก็บ: วันเวลา, **ประเภทการแก้**, **ผู้แก้**, **สาขา**, เอกสาร,
หมายเหตุว่าแก้เพราะอะไร และรายละเอียดก่อน/หลัง (มีปุ่ม "เปิดเอกสาร" ในฟอร์ม)

**เปิดดูได้ที่:** `บัญชี → การรายงาน → ประวัติการแก้ AI-IT`
(และที่ `การตั้งค่า → ตัวช่วย AI-IT → ประวัติการแก้` สำหรับผู้ดูแล)

สิทธิ์การเห็นข้อมูล: พนักงานทั่วไปเห็นเฉพาะของตัวเอง, ผู้ที่เข้าเมนูรายงานบัญชีได้
(`account.group_account_readonly` / `group_account_invoice`) และผู้ดูแล AI-IT
เห็นได้ทั้งหมด

> แยกจาก `npd.ai.it.session` โดยตั้งใจ — session คือบทสนทนา (มีทั้งที่คุยค้าง
> และยกเลิกกลางทาง) ส่วนตารางประวัติเก็บเฉพาะงานที่ทำสำเร็จจริง

## ไฟแสดงสถานะ AI

จุดกลมข้างรูปโปรไฟล์ของบอทในแชทบอกว่า AI พร้อมใช้หรือไม่:

| สี | ความหมาย |
| --- | --- |
| 🟢 เขียว | ตั้งค่า Gemini API key แล้ว เรียก AI ได้ |
| 🔴 แดง | ยังไม่ได้ตั้ง key — ระบบยังใช้งานได้ แต่จะอ่านคำตอบด้วย regex อย่างเดียว |

ทำโดย override `res.partner._compute_im_status()` เฉพาะ partner ของบอท
(`online`/`offline`) แล้วย้อมสีด้วย SCSS ที่เจาะจงผ่าน data attribute จึงไม่กระทบ
จุดสถานะของผู้ใช้คนอื่น

> ทำในเทมเพลตล้วน ไม่ patch คลาส JS เพราะ `PartnerImStatusIcon` ของ mail

## กับดัก JS ที่เจอมาแล้ว (อย่าเผลอทำซ้ำ)

**อย่าเปิดแชทด้วย `openChat({partnerId})`** — `mail.partner.getChat()` ปฏิเสธ
partner ที่ไม่มี `res.users` ด้วยข้อความ
*"You can only chat with partners that have a dedicated user."*
และบอทของเราจงใจไม่มี user (ไม่ต้องล็อกอิน ไม่ต้องมีสิทธิ์)

ให้เปิด **ห้องแชทตรง ๆ** แทน โดยฝั่ง Python ส่ง `channel_info` กลับมาด้วย:

```js
const Thread = this.env.models['mail.thread'];
const thread = Thread.insert(Object.assign(
    { model: 'mail.channel' }, Thread.convertData(result.channel_info)));
thread.open();
```

## ล้างประวัติแชทอัตโนมัติ

Scheduled Action **"ตัวช่วย AI-IT: ล้างประวัติแชทเก่า"** รันทุกวัน **ตี 4 เวลาไทย**
ลบข้อความในห้องแชทของบอทที่เก่ากว่า **14 วัน**

> ⚠️ `ir.cron.nextcall` เก็บเป็น **UTC** และ Odoo เทียบกับ `now() at time zone 'UTC'`
> ถ้าใส่ `04:00:00` ตรง ๆ จะกลายเป็น **11 โมงเช้าเวลาไทย** ไฟล์ data จึงตั้งเป็น
> `21:00:00` UTC ซึ่งเท่ากับตี 4 เวลาไทยของวันรุ่งขึ้น (ไทย = UTC+7 ตายตัว ไม่มี DST)
> เวลาที่เห็นในหน้าจอ Scheduled Actions จะแสดงตามโซนเวลาผู้ใช้อยู่แล้ว

| ตั้งค่า | ค่าเริ่มต้น |
| --- | --- |
| `npd_ai_it_assistant.chat_history_days` | `14` (ใส่ `0` = ไม่ล้างเลย) |

**สิ่งที่ถูกลบ:** เฉพาะ `mail.message` ในห้องแชทของบอทเท่านั้น
**สิ่งที่ไม่ถูกลบ:** ตาราง `npd.ai.it.history` (หลักฐานว่าใครแก้อะไร),
ประวัติใน chatter ของเอกสาร, และตัวเอกสารเอง

เหตุผลที่รัน **ทุกวัน** ไม่ใช่ทุก 14 วัน: ข้อความแต่ละข้อความมีอายุของตัวเอง
การกวาดทุกวันทำให้ข้อความหลุดอายุ 14 วันแล้วถูกลบทันที และแต่ละรอบลบทีละน้อย
(จำกัด 2,000 ข้อความ/รอบ) ไม่ล็อกตาราง `mail_message` ยาว ๆ แบบกวาดทีเดียว

บทสนทนาที่ค้างคาเกิน 14 วันจะถูกปิดเป็น "ยกเลิก" ไปด้วย — ไม่งั้นพนักงานพิมพ์อะไร
มาใหม่ ระบบจะไปต่อจากขั้นตอนเก่าที่ข้อความประกอบถูกลบไปแล้ว

## คำสั่งที่พิมพ์ได้ทุกขั้นตอน

| พิมพ์ | ผล |
| --- | --- |
| `เริ่มใหม่` (หรือ `เมนู`, `หัวข้อ`, `ทำใหม่`, `restart`) | กลับไปเลือกหัวข้อใหม่ในแชทเลย ไม่ต้องกลับไปที่แท็บ |
| `ยกเลิก` (หรือ `เลิก`, `จบ`, `cancel`) | ออกจากรายการที่ทำค้างอยู่ |
| `ยืนยัน` (หรือ `ตกลง`, `ทำเลย`, `ok`) | ยืนยันให้ระบบเติมสต๊อก (ใช้ตอนขั้นสรุปเท่านั้น) |
| `ทำต่อ` (หรือ `ต่อ`, `ตัดเลย`, `ตัดสต๊อก`) | ให้ระบบตัดสต๊อกต่อให้เลย (ใช้หลังเติมสต๊อกเสร็จ) |
| `ไม่ต้อง` | ไม่ต้องตัดต่อ จะไปกดปุ่มที่เอกสารเอง |

คำลงท้ายสุภาพไม่มีผล — `เริ่มใหม่ครับ` / `ยืนยันค่ะ` / `ยกเลิกนะครับ` ใช้ได้หมด
(ดู `_command_forms` ใน `models/ai_it_session.py`)

ทุกข้อความที่บอท "รอคำตอบ" จะต่อท้ายด้วยคำสั่งเหล่านี้ให้อัตโนมัติ พนักงานจะได้
เห็นทางออกทุกขั้นตอน ไม่ต้องจำจากข้อความแรก (ทำใน `_post_bot()` ตัวเดียว
ส่ง `commands=False` เมื่อมีข้อความถัดไปตามมาทันที จะได้ไม่ซ้ำ)

## กติกาความปลอดภัย

| เรื่อง | สิ่งที่ทำ |

| หน้าที่ของ AI | อ่านข้อความพนักงานให้เป็นตัวเลข (เลขเอกสาร / จำนวนสต๊อกจริง) เท่านั้น ถ้า AI ใช้ไม่ได้ ระบบถอยไปใช้ regex ต่อได้ |

| การสร้างคลัง | สร้างได้เฉพาะ **คลังลูก (internal)** ของสาขาที่ผ่าน `resolve_branch` แล้ว แขวนใต้คลังแม่ที่สาขาอื่นในบริษัทเดียวกันใช้อยู่ — **ไม่สร้าง warehouse / ประเภทการดำเนินการ / ลำดับเลขที่ใหม่** และไม่แตะ `branch_id` ของคลังที่เป็น view/stock/input/output ของ warehouse |
| การยืนยัน | ต้องพิมพ์ "ยืนยัน" ก่อนเสมอ ระบบไม่แก้ฐานข้อมูลเองจากข้อความเดียว |
| ร่องรอย | บันทึกทุกครั้งที่ `npd.ai.it.session` + `npd.ai.it.session.line` (ก่อน/เติม/หลัง) และเขียน log ฝั่งเซิร์ฟเวอร์ |

การเลือกคลังของสาขา และการเติมสต๊อกให้ถึงจำนวนสต๊อกจริง ใช้กติกาเดียวกับปุ่ม
"ตัดสต็อก Auto" เดิมในโมดูล `so_auto_stock_cut` เพื่อให้กดตัดสต๊อกต่อได้ทันที
(ปุ่มนั้นบังคับ `picking.location_id` ให้เป็นคลังของสาขาอยู่แล้ว คลังที่ตัวช่วย
สร้างขึ้นใหม่จึงถูกใช้ตัดสต๊อกได้เลย โดยไม่ต้องมี warehouse ของสาขาแยกต่างหาก)

ทุกครั้งที่สร้าง/ผูกคลังให้ จะถูกบันทึกลง **ประวัติการแก้ AI-IT**
(ประเภท "สร้าง/ผูกคลังของสาขา") และเขียน log ฝั่งเซิร์ฟเวอร์ด้วยว่าใครเป็นคนสั่ง

## การติดตั้ง

โมดูลอยู่ใน addons path อยู่แล้ว (`...\npd_dev\NPD_system\npd_dev`)

```
Apps → Update Apps List → ค้นหา "ตัวช่วย AI-IT" → Install
```

ต้องตั้งค่า Gemini API key ไว้ก่อน (ใช้ key ตัวเดียวกับโมดูล AI เดิม):

```
Settings → Technical → System Parameters
Key: advance_clear_ai_check.gemini_api_key
```

ถ้ายังไม่ได้ตั้ง key ระบบยังใช้งานได้ปกติ เพียงแต่จะอ่านคำตอบพนักงานด้วย regex
อย่างเดียว (รองรับ `1=10, 2=5` และการพิมพ์ตัวเลขเรียงตามลำดับ)

## การเพิ่มหัวข้อถัดไป

1. เพิ่มระเบียนใน **การตั้งค่า → ตัวช่วย AI-IT → หัวข้อ** พร้อมกำหนด `code`
2. เพิ่ม `code` นั้นใน `IMPLEMENTED_CODES` (`models/ai_it_topic.py`)
3. เขียนเมธอด `_handle_<code>(self, text)` ใน `models/ai_it_session.py`
   แล้วต่อ dispatch ใน `_handle_user_message`
